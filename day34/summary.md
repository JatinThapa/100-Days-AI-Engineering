# Day 34 – Evaluating RAG Pipelines

Today was a lighter learning day focused on **Evals for Retrieval-Augmented Generation systems**.

Building a RAG pipeline can involve a lot of experimentation, but evals provide a more scientific and quantitative way to measure whether the system is actually improving. Instead of relying only on whether an answer “looks good,” we can evaluate both the retrieval process and the final generated response using repeatable metrics.

## 1. Building a Golden Dataset

The first step is to create a **golden evaluation dataset** containing:

* Example user questions
* The correct or relevant source documents
* Reference answers representing an ideal response
* Important keywords or facts expected in the answer

This dataset acts as a benchmark against which different versions of the RAG pipeline can be tested.

It should also continue growing over time. New examples can come from developers, domain experts, failed queries and real users testing the product.

## 2. Measuring Retrieval Quality

The next step is to evaluate whether the retriever is surfacing the right chunks of information.

Some common retrieval metrics are:

### Mean Reciprocal Rank — MRR

MRR measures how highly ranked the **first relevant result** is.

If the first relevant chunk appears at:

* Rank 1, its reciprocal rank is 1
* Rank 2, it is 1/2
* Rank 3, it is 1/3

The reciprocal ranks are then averaged across all evaluation questions.

[
MRR = \frac{1}{N}\sum_{i=1}^{N}\frac{1}{rank_i}
]

An MRR of 1 means that a relevant chunk was ranked first for every question.

### Normalized Discounted Cumulative Gain — nDCG

nDCG evaluates the quality of the entire ranking rather than looking only at the first relevant result.

Relevant chunks receive more credit when they appear near the top of the retrieved list. Results appearing further down contribute less because of a logarithmic discount.

[
DCG@K = \sum_{i=1}^{K}\frac{2^{rel_i}-1}{\log_2(i+1)}
]

DCG is then compared with the best possible ordering, known as the Ideal DCG:

[
nDCG@K = \frac{DCG@K}{IDCG@K}
]

A score closer to 1 means that the most relevant chunks are consistently ranked near the top.

### Recall@K

Recall@K measures how many of the known relevant documents were successfully retrieved within the top K results.

[
Recall@K =
\frac{\text{Relevant chunks retrieved in top K}}
{\text{Total known relevant chunks}}
]

High recall is especially important in RAG because the model cannot use important information that was never retrieved.

A related but slightly different metric is **Hit Rate@K**, which checks whether at least one relevant result appeared anywhere in the top K.

### Precision@K

Precision@K measures how much of the retrieved context is actually relevant.

[
Precision@K =
\frac{\text{Relevant chunks in top K}}
{K}
]

For example, if three out of five retrieved chunks are relevant, Precision@5 is 0.6.

Recall helps ensure that important information is not missed, while precision helps avoid filling the LLM’s context window with irrelevant or distracting content.

## 3. Measuring the Generated Answer

After evaluating retrieval, the final answer generated by the LLM can be compared with the reference answer from the golden dataset.

A basic approach would be to compare matching words or keywords. However, this often fails because two answers can express the same meaning using completely different wording.

A more practical method is to use an **LLM as a judge**. The evaluator model can score the generated answer using criteria such as:

* Accuracy
* Completeness
* Relevance
* Faithfulness to the retrieved context

Answer evaluation is more directly aligned with the user’s experience, but it can also be less predictable because the generator and evaluator are both language models.

Retrieval evaluation is usually easier to control and improve through changes to chunking, embeddings, search parameters, reranking and metadata filtering.

The main takeaway from today was that a strong RAG system should not be judged by intuition alone. By maintaining a golden dataset and measuring both retrieval quality and answer quality, improvements to the pipeline can be tested objectively instead of relying on guesswork.
